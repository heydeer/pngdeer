# TinyPNG 在 UI 截图上赢在哪里，以及怎么用 libimagequant 补上

2026-10-23，基于 `bench/` 的 109 张公开图片（其中 15 张网页截图）。分数是 SSIMULACRA2，体积是 oxipng 之后的字节数。“同画质体积比”是把 TinyPNG 的结果放到开源方案的“体积–画质”曲线上插值，算开源达到同样分数需要的字节数 ÷ TinyPNG。

## 结论

1. **TinyPNG 没有特殊格式**：UI 截图同样是 ≤256 色的调色板 PNG。差距在于调色板怎么分配。
2. **libimagequant 的调色板按“像素数 × 均方误差”分配**。UI 截图里大片近似的颜色（暗色背景的细颗粒噪声、浅灰底色）占了绝大多数像素，于是吃掉了大部分调色板槽位；像素少但很醒目的颜色（强调色图标、文字颜色）分不到槽位，结果：
   - `linear@2x`：64 色时蓝色图标整个变成灰色，黄色图标偏色；分数从 96 色时的 91.2 掉到 81.4。TinyPNG 只用 39 色就保住了这些颜色（88.9 分）。
   - `react-dev@2x`：14 色时搜索框的灰色文字不在调色板里，只能靠抖动“拼”出来，文字边缘全是点状噪声；TinyPNG 用 30 色，文字干净。
3. **pngquant 的 `--quality` 也是基于均方误差的**，在 UI 上会选出过少的颜色（`linear@2x` 在 q95 只有 22 色），而且档位之间会跳变（q98 是 80.3 分 / 536KB，q100 直接是 93.8 分 / 852KB），中间没有可选的点。
4. **补法只用 libimagequant 的公开 API**，不需要改库：
   - 先量化一遍，算出每个像素的误差；
   - 用 `set_importance_map` 把误差大的像素权重调高（重要度 = 32 + 8 × 最大通道误差，上限 255），再量化一遍；
   - 用 `set_max_colors` 直接搜索颜色数，不用 `--quality`。

## 接进 bench 后的真实效果（压缩时实时搜索）

`bench.py` 的 `liqT` 方案：对每张图、每种抖动强度，按对数二分搜索 liqx 的颜色数（两遍误差反馈，增益 8），找到达到目标分数的最小文件。全部 109 张图，目标 70/75/80/85/90/95 连成曲线：

| 方案 | 同画质体积比（中位数） | 同画质体积比（总） | 够不着 | 同体积分差（中位数） |
|---|---|---|---|---|
| auto（pngquant 实时搜索） | 93.2% | 95.3% | 28 | +0.4 |
| **liq（liqx 实时搜索）** | **89.2%** | **88.2%** | **18** | **+1.0** |
| 参照：所有 pq 档位事后挑最优 | 94.5% | 94.8% | 22 | +0.5 |

- liq 在 91 张能比较的图里有 80 张比 TinyPNG 小；按分类（同画质体积比中位数 / 总）：3D 85.4% / 86.5%，照片 85.8% / 85.9%，带透明的照片 82.2% / 83.0%，网页截图 93.7% / 95.7%（15 张全部够得着），插画 93.6% / 95.0%，图标 92.2% / 93.8%。
- 固定目标：`liq90` 体积是 TinyPNG 的 93.1%（中位数）/ 96.9%（总），分数中位数还高 0.6；`liq85` 是 83.3% / 91.7%，分数低 1.5。
- 还够不着的 18 张差距都很小（多数 < 1 分）。其中 6 张 twemoji 图标是因为最高目标只设到 95，而 TinyPNG 在这些图上是 95–100 分；其余是 3D 和插画的高画质端。
- 输得最多的是 `react-dev@2x`（117%）、`reinel-compass-rose`（117%）、`linear@2x`（114%）。`react-dev` 主要是目标档位太稀：liq85 是 15 色 86.5 分 / 64KB，liq90 要 123 色 90.1 分 / 200KB，TinyPNG 的 88.7 分落在中间，插值高估了；网格实验里 32 色就有 88.8 分 / 98KB。

耗时（`-j 1`，一次一张图，`bench/results/timing-j1`）：

| 分类 | auto85 | liq85 | TinyPNG（API 往返） |
|---|---|---|---|
| 全部（中位数 / 平均） | 1.82 / 2.75 秒 | **1.49 / 2.36 秒** | 3.42 / 3.54 秒 |
| 3D / 图标 / 照片 | 0.5–1.1 秒 | 0.5–0.8 秒 | 2.0–3.9 秒 |
| 带透明的照片 | 2.2 秒 | 2.2 秒 | 6.3 秒 |
| 插画 | 5.1 秒 | 4.0 秒 | 3.7 秒 |
| 网页截图 | 4.1 秒 | 3.6 秒 | 2.7 秒 |

liqx 每次量化只要 0.1–0.2 秒（5MP），两遍量化几乎不加时间；耗时主要在每次候选都要跑的 SSIMULACRA2（5MP 约 0.6 秒）。liq 每个目标中位数 16 次评估，比 auto 的 19 次少。

## 第二轮：调参、小图规则

在 24 张测试子集（偏向难图）上试了几种改法，同画质体积比（中位数 / 总）：

| 变体 | 体积比 | liq85 平均耗时 | 评估次数 |
|---|---|---|---|
| 第一轮默认 | 93.1% / 89.1% | 4.67 秒 | 15.5 |
| libimagequant speed 1 | 89.5% / 86.5% | 4.65 秒 | 15.5 |
| 只试 0.5 和不抖动两种抖动 | 94.2% / 89.0% | 3.12 秒 | 11 |
| **两者一起（新默认）** | **88.6% / 86.3%** | **3.40 秒** | **11** |
| 再加颗粒区域降权 | 95.0% / 82.9% | 3.61 秒 | 11 |

颗粒降权让透明照片和网页截图更好，但 3D 明显变差（83.5% → 98.4%），没有采用。误差反馈增益 4 / 12 没有稳定的提升；zopfli 在 5MP 图上多花 17 秒只省 0.9%，也没用。

盲测里一张 72px 的灯泡图标（`twemoji-1f4a1`）被看出来比 TinyPNG 差：我们合并了几档边缘半透明、丢了灯座条纹的过渡色，而 SSIMULACRA2 在这么小的图上几乎测不出来（95.1 对 95.4）。加了两条规则：

- **小图放大打分**：长边小于 256 的图，原图和所有输出（包括 TinyPNG 的）都先按最近邻放大到不小于 256 再打分。
- **少色图优先无损**：原图不超过 256 种颜色、无损调色板版本不超过选中结果 1.15 倍时直接用无损。21 张少色图都触发过。

全部 109 张（liq 目标 70–95 连成曲线，和 TinyPNG 比）：

| | 同画质体积比（中位数 / 总） | 比 TinyPNG 小 | 够不着 | 同体积分差 |
|---|---|---|---|---|
| 第一轮 | 89.2% / 88.2% | 80 / 109 | 18 | +1.0 |
| **第二轮** | **88.0% / 85.7%** | **88 / 109** | **13** | **+1.6** |

- 10 张 twemoji 全部够得着了，同画质体积是 TinyPNG 的 94.7%–99.8%。灯泡：liq90 是 32 色、595 B、90.6 分，TinyPNG 是 615 B、90.0 分（按放大 4 倍打分）。
- 按分类（中位数）：3D 83.2%，照片 84.5%，透明照片 80.4%，插画 92.0%，网页截图 94.4%，图标 94.3%（图标的打分方式变了，和第一轮不直接可比）。
- 还够不着的 13 张：6 张 3D、7 张插画，差距多数不到 1 分；最大是 `fluent-red-apple`（3.5 分）。

耗时（`-j 1`，`bench/results/timing-j1-v2`），中位数：liq85 **1.24 秒**（第一轮 1.49 秒），TinyPNG API 往返 3.42 秒；按分类 liq85 全部快于 TinyPNG：网页截图 2.62 对 2.70 秒，插画 2.76 对 3.73 秒，其余 0.5–2 秒对 2–6 秒。另外最后一步 oxipng 从 `-o max` 换成 `-o 2`，体积只多 0.35%，耗时降到约 30%，还没用在 bench 里。

## 用独立指标复核（butteraugli）

liq 的搜索本身就在优化 SSIMULACRA2，再用 SSIMULACRA2 和 TinyPNG 比，会偏向我们。所以用 jpeg-xl 自带的 butteraugli 对第二轮全部 109 张的输出重新打分（越小越好；透明图叠在深色和浅色背景上各算一次取较差；图标按原尺寸，不放大）：

| 指标 | 方案 | 同画质体积比（中位数 / 总） | 比 TinyPNG 小 | 够不着 |
|---|---|---|---|---|
| SSIMULACRA2（参照） | liq | 88.0% / 85.7% | 88 / 109 | 13 |
| butteraugli 3-norm | **liq** | **88.3% / 81.7%** | 83 / 109 | 12 |
| butteraugli 3-norm | auto | 94.9% / 92.5% | 62 / 109 | 29 |
| butteraugli 最大距离 | **liq** | **84.9% / 76.3%** | 84 / 109 | 13 |
| butteraugli 最大距离 | auto | 94.3% / 87.1% | 52 / 109 | 39 |

- 按体积配对（和盲测一样，取体积最接近 TinyPNG 的 liq 输出）：liq 的 butteraugli 距离更小的有 **81** 张，TinyPNG 更小的 27 张，持平 1 张。3D 19 : 3，照片 11 : 1，透明照片 15 : 1，网页截图 12 : 3，插画 14 : 10，图标 10 : 9（图标基本打平）。
- 两个指标对“谁更好”的判断在 107 组里有 99 组一致（93%）。
- 结论：优势不是靠迎合 SSIMULACRA2 得来的，换一个独立指标依然成立，总体积上还更大。但两个都是算法指标，还缺人眼盲测和一批没参与调参的新图。

## 第三轮：邻居平滑（`liqx --rdo`）

想法：两个调色板颜色误差差不多时，选和左边或上边邻居相同的那个，让图像数据更容易压缩。实现成 liqx 的 `--rdo DELTA`：重映射之后逐像素检查，当前颜色和左、上邻居都不同时，如果某个邻居的颜色误差最多只多 DELTA（预乘透明度后的 RGBA，取最大通道差），就换成它。

- **全局打开会帮倒忙**（24 张测试子集）：DELTA 1 / 2 / 4 时，同画质体积比（总）从 86.2% 变成 102.9% / 100.1% / 112.0%，够不着的图从 4 张变成 14 / 16 / 19 张。平滑会把抖动图案抹回成色带，用满 256 色也到不了高画质。
- **作为搜索的一个变体**（每个颜色数同时试 0.5 抖动、不抖动、不抖动 + 平滑，取达标的最小文件）：平滑变体被选中约三分之一，测试子集上只省 0.5%，全量上好一些：

| 指标 | 方案 | 同画质体积比（中位数 / 总） | 够不着 |
|---|---|---|---|
| SSIMULACRA2 | 不平滑 | 88.0% / 85.7% | 13 |
| SSIMULACRA2 | + 平滑变体（DELTA 2） | 87.1% / 84.9% | 14 |
| butteraugli 3-norm | 不平滑 | 88.3% / 81.7% | 12 |
| butteraugli 3-norm | + 平滑变体（DELTA 2） | 87.8% / 78.5% | 13 |

收益主要在插画、透明照片和网页截图，比预想的 5–15% 小得多：平滑损失的画质要靠更多颜色补回来，一来一回大部分抵消。评估次数中位数从 11 变成 13。已设为 liq 的默认变体（`--liq-variants 50,0,0r2`）。真正的码率–失真优化要把压缩代价放进抖动和重映射本身，而不是事后平滑。

## 第四轮：搜索搬进 liqx，浏览器原型

- **进程内搜索**：liq 的搜索整个移进 liqx（`liqx --target T`）。原图只解码一次、参考图只算一次，每个颜色数只量化一次、按变体重新映射，候选用 fast-ssim2 在内存里打分。fast-ssim2 和 libjxl 的 ssimulacra2 在 164 组样本上平均差 0.000、最大 0.22；它的条带模式会偏 2.4 分，没用。最后一步 oxipng 改成 `-o 2`。
- **单线程计时**（`bench/results/timing-j1-v4`）：liq85 中位数 **0.60 秒**、平均 0.90 秒（之前带平滑是 1.63 / 2.46 秒），TinyPNG API 往返 3.42 秒；网页截图 1.41 对 2.70 秒，插画 1.17 对 3.73 秒，每个分类都比 TinyPNG 快。
- **体积**基本不变：SSIMULACRA2 下同画质体积比 89.0% / 85.8%（中位数 / 总），butteraugli 下 89.3% / 79.4%；中位数比上一轮差约 1 个百分点，是 `-o 2` 的代价。
- **浏览器原型**（`web/`）：liqx 拆成库，PNG 读写换成纯 Rust（png crate 解码 + 自写编码器，miniz 压缩），编译成 WASM（554 KB）。功能完整、结果和原生一致，但：
  - 慢：单线程，fast-ssim2 在 WASM 上没有 SIMD。示例图 1.4–18.6 秒，5MP 截图 74.6 秒，大约是原生的 5–20 倍。
  - 大：纯 Rust 编码器比 oxipng `-o 2` 大（中位数 +7.8%，总 +11.3%），浏览器版对 TinyPNG 只剩 92.5% / 97.3%。差距来自 libdeflate 级别的压缩和调色板排序。（第五轮把 oxipng 编进了 WASM，这个差距已消除。）

## 第五轮：浏览器版提速

目标是 5MP 截图在浏览器里 10 秒以内（之前 63–82 秒）。两部分：打分本身变快，再加缩小图粗搜。

- **打分快了 3 倍多，分数不变**。剖析 WASM 发现 64% 的时间花在 `fmaf` 上：WASM 没有标量的融合乘加指令，fast-ssim2 标量路径里的每个 `mul_add` 都变成 compiler-builtins 的逐位软件模拟。直接换成普通乘加不行，递归高斯滤波会把舍入误差放大，分数最多偏 2.4；改成在 f64 里算（f32 乘积在 f64 里是精确的）就和原生一致到小数点后 4 位。另外两处：纵向模糊原来一列一列地走（每步跨一整行，缓存全失效），改成 64 列一块按行走；转 XYB 时和前一个像素相同就复用结果（截图大片纯色，调色板图更是如此）。三处都打在 `web/wasm/vendor/fast-ssim2` 里，只有浏览器版用。一次 5MP 打分 6.5 秒 → 2.0 秒，原图上的完整搜索 74.6 秒 → 约 30 秒。WASM SIMD 版仍然更慢（同样要精确模拟融合乘加），没开。
- **缩小图粗搜，原图确认**（`--preview-pixels 350000`）。先在不超过 35 万像素的缩小图（加权平均缩小）上做完整搜索，然后：
  - 缩小图上的分数系统性偏高（中位数高 4.5 分，最多高 18 分），而且偏差随颜色数变化（react-dev：104 / 62 / 18 色时分别是 +0.5 / −0.8 / +3.4），所以只确认一次不够：一次确认时 76 张里有 29 张掉到 85 以下。改成预算 3 次的原图确认：第一次之后用量到的偏差修正目标，在缩小图上重新找颜色数（便宜）；两边都有原图分数后，在 log(颜色数) 上插值。粗搜目标加 2 分余量，平均 2.9 次原图打分。
  - 抖动在原图上比在缩小图上贵得多，缩小图常选错变体（40/76 张和完整搜索不同，react-dev 选了 d50 15 色，比 d0r2 30 色大 48%）。改成按原图的粗略编码体积（不过滤、deflate 1 级）给变体排序，再确认；有剩余预算时再试第二名。
  - 分数到不了目标的图（256 色也不够）在原图上按原规则选变体，画质和完整搜索完全一样（32 张）。
  - 试过但更差的：隔点抽样代替平均缩小（偏差更大）、从原图挑小块拼图（调色板只看到局部颜色，最差偏 137 分）、25 万像素预览（没更快）。
- **结果**（109 张，目标 85，原生跑同样的流程）：76 张走缩小图，没有一张掉到 85 以下；总体积比原图完整搜索大 1.5%，中位数持平。浏览器（Chrome，一次一张）里 8 张 5MP 截图 **5.3–8.9 秒**；8 张一起丢进去（4 个 worker）共 19 秒。
- **oxipng 进浏览器**：oxipng 开 `freestanding` 特性就能编译成 WASM（libdeflate 用 Homebrew 的 clang 编），输出和原生 `oxipng -o 2` 逐字节相同。最终文件改交给它，自写编码器只用来排候选（去掉了最后那次 miniz 10 级重压）。浏览器版 109 张总体积 **−10.1%**（中位数 −7.1%），和"旧输出再过原生 oxipng"一模一样；3 张因为候选改按 4 级体积排序选了略不同的颜色数，合计差 326 字节。少色图规则里，自写编码器的无损版本如果连缩小 25% 都进不了 15% 的余量就不再过 oxipng（实测 oxipng 最多只缩小 14%）。5MP 截图 Chrome 里 **5.9–9.3 秒**，oxipng 占 0.5–1.2 秒；8 张一起 20 秒。WASM 从 627 KB 变成 872 KB。
- **已经压过的图**（用户拖进来一张 TinyPNG 之类压过的 256 色照片，1254²，590 KB）：网页只做了无损优化（省 12 字节），而原图上完整搜索在 80 档能到 333 KB。两个原因：平均缩小把调色板图的抖动磨平、还造出原图没有的颜色，缩小图上平滑（d0r2）够不着目标就被排除了，而原图上它恰恰最好（原调色板 + 平滑：84.4 分、333 KB；不平滑要 192 色才到 82.8、495 KB）；另外原图本来就是 256 色，256 色时原样复现（100 分），这一下跳变把后面的插值带偏。改动：图片不超过 256 色时，缩小图改成每块取中心点（保留原有颜色和颗粒）；原图确认没达标时，下一步最多升到 3 倍颜色数（大缺口处量到的偏差高估了上面的偏差，vercel@2x 原来一步跳到 256 色，最后停在 77 色，现在 32 色，完整搜索是 24 色）。
  - 那张照片：80 档 590 KB → **333 KB**（84.4 分）；TinyPNG 同一张给出 498 KB、82.5 分。85 档仍然保留原文件（完整搜索也是）。
  - 测试集：拿 bench 缓存的 126 张 TinyPNG 输出（超过 35 万像素）当"已压过"的输入，比原图上完整搜索：85 档 +4.1% → +1.9%，80 档 +4.5% → +1.6%；109 张原图 +1.6% → +1.3%。都没有一张掉到目标以下，5MP 耗时不变。

## 第六轮：自动画质（不用选档位）

- **TinyPNG 没有固定画质**：109 张上它的分数从 65.8 到 100（中位数 87，照片约 81，图标约 93）。它也不是"每涨 1 分多花多少字节就停"：在我们的曲线上，它停的位置斜率从每翻倍 5 分到 51 分都有。和它最像的是 **pngquant 用满 256 色**（`--quality 0-100`）：分数中位数只差 1.0、离散 1.0；另外 256 色本来就近乎无损（≥95 分）时，它会少用颜色停在 89–93。
- **规则**（`liqx --target auto`）：参考分 = 普通 libimagequant 256 色（speed 4，Floyd–Steinberg 抖动，不做误差反馈）的分数，但不低于我们自己 256 色最好结果 − 4（个别带透明的线稿上普通量化比 TinyPNG 和我们都差 10 分以上）；原图不超过 256 色时普通量化会原样复现，改用我们 256 色里最好的非复制结果（你那张头像：平滑版 84.4）。目标 = min(参考分, 90)。90 是 1:1 看不出区别的线，再往上花字节看不出来。
  - 调过的参数：参考分减 0 / 0.5 / 1，上限 90 / 91 / 92 / 95。"我们 256 色最好 − 1"做参考更差（UI 上我们的天花板比普通量化高很多，目标定得太高）。
- **结果**（109 张，对 TinyPNG）：原图上完整搜索体积 90.1%，分数中位数高 0.5，比 TinyPNG 小且不差的 66 张；浏览器流程（缩小图粗搜）体积 90.9%，中位数高 0.6。"看得出更差"（低于 90 且比 TinyPNG 低 1 分以上）只有 5–6 张，多是 TinyPNG 的 256 色本身比我们好的那几张。对照：固定 85 档 87.5% 但中位数低 1.4、55 张看得出更差；固定 90 档 93.9%、高 1.0、4 张。
- **浏览器流程配套改动**：目标由原图上一次普通量化打分决定（缩小图估出来的目标会偏 ±1.5 分）；缩小图加了余量够不着时先不加余量再试；第一名变体 256 色也够不着就接着试下一个，而不是直接把所有变体都按 256 色算；超出确认次数时取分数最高的结果。
- **还没解决**：5MP 截图单线程 Node 里 11–19 秒（第七轮多线程后 Chrome 里 4.8–8.4 秒）；`react-dev@2x`、`linear@2x` 这种最后几分特别贵的图，TinyPNG 用 30–40 色停在 89 左右，我们按上限 90 走，体积是它的 1.8 / 1.2 倍。

## 第七轮：多线程 WASM

- **做法**：`web/wasm` 加 `threads` 特性（wasm-bindgen-rayon），另编一份 `web/pkg-mt`。要 nightly Rust（`-Z build-std` 带原子操作重编标准库）、C 代码也加 `-matomics -mbulk-memory`，并且要手动传 `--shared-memory --import-memory --max-memory` 和 TLS 导出（新版 Rust 不再自动传，不传的话内存不是共享的，`postMessage` 报 `Memory could not be cloned`）。fast-ssim2 每个尺度的 9 次模糊本来就是 rayon 并行的互不依赖的任务，libimagequant、oxipng 也有 rayon 路径，输出和单线程逐字节相同。
- **速度**（自动画质，8 张 5MP 截图，Chrome 156，一次一张，14 线程）：**4.8–8.4 秒**，单线程是 10.8–19.1 秒。打分快 2.6 倍；量化、映射和我们自己的代码（误差反馈、平滑、编码）基本还是单线程，是剩下的大头。
- **内存**：5MP 峰值 1.3 GB（大头是 fast-ssim2 的参考金字塔和每次比较的临时缓冲，约 800 MB），12MP 2.7 GB，15MP 3.4 GB，20MP 超过 wasm32 的 4 GB。顺手把搜索缓存的量化图像（每个约 95 MB）限到最近 3 个，峰值只降了 5%，结果没变。多线程版里某个线程内存用尽会让整个压缩卡住，所以 1200 万像素以上交给单线程版（会正常报错），1600 万以上直接拒绝。
- **坑**：一个页面里第二个多线程实例会卡住，所以多线程时只开一个 worker（批量 8 张 5MP 共 48 秒，比单线程四个 worker 并行略慢，单张快一倍多）。Claude 应用内置浏览器里，多线程实例在用时刷新页面，同一进程里之后的 WebAssembly（连单线程版）都会卡住；真 Chrome（无头，独立配置）连刷三次都正常，是内置浏览器的问题。页面加了自检：多线程 worker 先压一张小图，5 秒内没完成就退回单线程。

## 第八轮：高画质端（256 色天花板）

- **问题**：14 张图（6 张 3D、8 张插画）上 TinyPNG 的画质比我们 256 色能到的最高还高，差 0.1–3.5 分；自动画质下"看得出更差"的 5–6 张基本都是它们。
- **原因**（在这 14 张上把误差反馈强度 × 抖动强度全试一遍，都按 256 色打分）：
  - 我们的变体没有满抖动（只有 50% 和 0%）。平滑渐变多的 3D / 插画在 256 色时满抖动常常最高（mahuri 78.4 对 50% 的 76.3）。
  - 误差反馈把调色板槽位让给少见的颜色，这对 UI 很关键，但在 256 色的平滑图上反而亏：不做误差反馈的普通调色板在 renal-corpuscle 上 86.6 对 84.5，digestive-system 85.0 对 83.8。
  - 每张图各取最好的组合，14 张里 8 张能追上 TinyPNG（原来 0 张）；剩下只有 red-apple 差得多（84.5 对 85.7）。它的调色板结构和 TinyPNG 一样（255 色、37 个半透明项），只是不透明像素的平均误差 1.64 对 1.59，是调色板优化本身的差距。
- **改法**（不进常规搜索，免得变慢）：256 色时多两个候选：我们的调色板满抖动、普通调色板（libimagequant speed 4，即 pngquant 默认，不做误差反馈）满抖动。普通调色板本来就是自动画质的参考分，已经算过，不额外花时间。常规变体在 256 色时离目标还差 0.5 分以上，才考虑这两个候选，而且要划算：每多 1 分（只算到目标为止）最多多 15% 字节。不加这条的话，tinypng@2x 会为了 1 分多花 30%（比 TinyPNG 还大），stripe@2x 在浏览器里会多花 50%。
- **结果**（自动画质，对 TinyPNG）：原图完整搜索体积 90.8%（之前 90.1%），分数中位数 +0.7（之前 +0.5），看得出更差 3 张（之前 5）；浏览器 91.6%（之前 90.9%）、+0.7（之前 +0.6）、4 张（之前 6）。14 张难图里 3 张追上 TinyPNG，差距中位数从 −0.9 缩到 −0.3/−0.4。5MP 截图浏览器 4.8–9.6 秒（tinypng@2x 多一次原图打分）。
- **还能做的**：剩下的差距在调色板优化本身（red-apple 那种）：在感知色彩空间里对整张图再做几轮 k-means，或者直接按 SSIMULACRA2 微调调色板。

## 第九轮：调色板精修

工具：`tools/liqx/examples/palette_lab.rs`（第十三轮随 libimagequant 一起删掉了），在 256 色下比较不同调色板和映射方式的分数。

- **差距在调色板还是在映射？** 把 TinyPNG 输出里的调色板拿出来，用 libimagequant 的抖动重新映射原图：14 张难图里多数比 TinyPNG 自己的输出还高（teddy-bear 88.8 对 87.8，mahuri 78.6 对 77.7，potted-plant 89.1 对 88.7），也高过我们所有的调色板。所以多数图上 TinyPNG 赢在调色板，映射反而是我们的好。例外是 red-apple：TinyPNG 的调色板用我们的映射只有 84.6，和我们自己的差不多，它的 85.7 来自映射（输出里 85% 的不透明像素就是最近色，只轻微抖动）。
- **自己写映射**：最近色、不同强度的 Floyd–Steinberg（sRGB / 线性光）、Bayer 有序抖动。75% 强度的 FS 在 red-apple 上比 libimagequant 高 0.6、mouse-mechanism 高 1.2，但中位数低 1.0–1.4 分（libimagequant 有边缘图、误差上限和映射时的 k-means），没采用。
- **TinyPNG 的调色板好在哪**：OKLab 里每个像素到最近调色板色的平均距离和我们一样，但 99 分位更小（teddy 1.71 对 1.78，digestive 5.25 对 5.70）：照顾到了最难还原的少数颜色。误差反馈（增益 8）照顾得太狠，普通调色板不照顾。
- **精修**：在 OKLab 里对整张图的不透明颜色做几轮 k-means，每种颜色按像素数 × 距离^(p−2) 加权（p=2 是普通 k-means，p 越大越偏向难还原的颜色），半透明项不动，再用 libimagequant 按这个固定调色板映射。p=3、5 轮最好用：mahuri 79.5（原来最好 78.1，TinyPNG 77.7），red-apple 85.3（84.5 / 85.7），teddy-bear 88.8（87.8 / 87.8）；但没有哪组参数处处都好（p=4 在一张扁平配色的地图上掉 29 分），所以做成第三个 256 色候选，靠打分挑。
- **接进搜索的几个细节**：候选之间按"多花的字节划算不划算"挑，达标的候选里选分数最高的（原来按字节最小，精修版永远选不上）；"达到目标就挑最小文件"那一步不能覆盖顶端挑出来的结果；参考分的保护线从比我们最好低 4 分收紧到 3 分（stripe@2x 因此 79.3 分超过 TinyPNG，多 3% 字节）；普通候选已经超出最大允许体积时，就不再做满抖动和精修候选（tinypng@2x 在浏览器里从 11.5 秒回到 8.6 秒，结果不变）。精修的最近色查找按亮度排序剪枝，结果不变、快几倍。
- **结果**（自动画质，109 张，对 TinyPNG）：完整搜索体积 91.0%，分数中位数 +0.72，看得出更差 2 张（第八轮 3 张，第七轮 5 张）；浏览器 91.6%、+0.72、3 张（之前 4 / 6）。14 张难图的平均差距 −1.27 → −0.80 → **−0.69**（含 5 张我们按上限停在 90、TinyPNG 在 91–93 的图）。5MP 截图浏览器 4.8–8.6 秒。
- **还剩的**：nueva-esparta（参考分用的普通调色板在这张图上比我们和 TinyPNG 都差 3 分，自动目标定低了）、potted-plant（候选够得着，但小文件多 16% 以上字节，划不来）、red-apple 差 0.4（映射）。

## 第十一轮：和其他开源量化器横向比较

`bench.py` 加了 `<工具>N` / `<工具>N-d0` 方案：ImageMagick（`-colors`，PNG8）、FFmpeg（palettegen / paletteuse）、Pillow（median cut；有透明时 fast octree）、exoquant（k-means）、quantette（Wu + k-means，Oklab）、NeuQuant（color_quant）、quantizr（imgproxy）；后四个是 Rust 库，用 `tools/quantlab` 调。每个工具跑 16 / 32 / 64 / 128 / 256 色 × 抖动 / 不抖动，pngquant 跑 5 个档位 × 抖动 / 不抖动，都过同样的 `oxipng -o 2`（`bench/results/tools-main-20261024-222124`、`bench/results/tools-holdout-20261024-222124`）。

这些工具没有"目标画质"，所以把每个工具的 10 个输出并成一条体积–画质前沿（相当于事后替它每张图挑最好的设置，对它们是偏宽的），看两件事：能不能达到 TinyPNG 的画质（"够得着"），以及在 TinyPNG 的文件大小下分数高多少（中位数）。ImageMagick、FFmpeg、quantette 的调色板 PNG 只有全透明 / 不透明，所以另算一遍只看不透明的图。用 `experiments/palette-feedback/tool_rank.py` 算：

## 第十二轮：quantette 调色板做不透明图的候选

第十一轮里 quantette 在不透明图上和我们差不多，它的调色板（Oklab 里 Wu 初始化 + k-means）和 libimagequant 的出发点不同，可能在一些图上更好。liqx 加了第四种调色板来源 `Source::Kmeans`（`quantize::kmeans_palette`）：quantette 出调色板，作为固定色交给 libimagequant 重新映射（抖动也是 libimagequant 的）。图里只要有一个像素不是完全不透明就不用它（quantette 不处理半透明）。用在两处：

- **常规变体**：在每个颜色数上和 d50 / d0 / d0r2 一起试，标签 `q` 开头（`q0` 不抖动）。自动画质、完整搜索下比了三种加法，总体积变化（109 张 / 71 张）：`q0` −1.39% / −1.35%，`q50` −0.85% / −1.24%，`q0` + `q50` −0.99% / −1.53%。`q0` 两组都稳、评估次数少，默认变体改成 `50,0,0r2,q0`。
- **256 色的补充候选**：满抖动的 quantette 调色板（`q100`），和满抖动、普通、精修三个候选一样按每分 15% 的规则选。只在 mahuri 上被选中。

## 第十三轮：不用 libimagequant

libimagequant 是 GPL-3.0（或商业授权），是 liqx 依赖里唯一的 copyleft：oxipng 是 MIT，libdeflate 是 MIT / Apache-2.0，fast-ssim2 是 BSD-2，quantette 和 palette 是 MIT / Apache-2.0。想用 MIT / Apache 发布就得换掉它。这一轮先量换掉要付出多少，结果是压缩率不降反升，于是直接去掉了它。

`tools/liqx/src/permissive.rs` 是自己写的调色板生成和映射，只用教科书方法，没有参考 libimagequant 的代码：加权中位切分（每个盒子在最能降低平方误差的位置切开）加加权 k-means 生成调色板；映射用最近色，或蛇形 Floyd–Steinberg，在边缘和纹理处减弱抖动。比较时它和 libimagequant 并存（`liqx --backend own`），搜索、自动画质、四种调色板来源都不用改（quantette 的调色板也走这个映射）。

调参工具 `tools/liqx/examples/backend_lab.rs`（和下面的 `reference_lab.rs` 都要 libimagequant 做对照，去掉它时一起删了）：在 16 / 64 / 256 色、三档抖动下，把 {libimagequant, 自己} 的调色板 × {libimagequant, 自己} 的映射交叉组合，分开看调色板和映射各差多少。只在 `bench/images` 的 26 张上调（18 张各类抽样，加 8 张高画质端的难图），留出集没参与。依次发现的问题：

- **颜色空间**：最初在 gamma sRGB 里算距离，最近色映射就比 libimagequant 低 2.2 分（kodim23 低 7.7）。换成 Oklab 后反而高 0.2，调色板在 256 色时也比它好。
- **满抖动**：误差上限 48 时比 libimagequant 低 2.4 分、大 11%；上限 6、误差小于 1.5 不扩散之后持平（256 色 −0.03 分、+3% 字节）。
- **误差反馈**：增益 8（为 libimagequant 调的）会伤到 k-means，16 色时低 4 分；增益 1 在 64 / 256 色最好。
- **半透明**：Oklab 值乘 alpha 描述不了合成后的样子，8 张难图（都带透明，多数是透明背景上的线稿图）差 0.6–1 分。改成"颜色叠在深灰 24、浅灰 232 上，两个结果在 Oklab 里的六个坐标"（正是基准给透明图打分用的两个背景；纯黑纯白在一张图上崩掉 21 分）。再让半透明像素不参与抖动（误差会顺着抗锯齿边缘漏进旁边），满抖动从 −1.2 分变成 +0.3 分。
- 最终 26 张、全部自己做 vs 全部 libimagequant：256 色 +0.45 到 +0.80 分，64 色 +0.83 到 +2.35 分，字节相近或更少。16 色抖动在几张复杂插画上很差，但那里所有方法都低于 60 分，搜索不会去。

自动画质的参考分原来是 libimagequant 普通调色板（speed 4、满抖动）的分数，它恰好很贴 TinyPNG 的画质。换成自己的普通调色板、半抖动、减 1.4 分（`REFERENCE`，用 `examples/reference_lab.rs` 在两个图集上挑的）：和 TinyPNG 分数的相关系数 0.96 / 0.92，libimagequant 的是 0.94 / 0.96。

最终版本（去掉 libimagequant、提速之后）的结果，`bench/results/nolq-main-20261025-102740`、`bench/results/nolq-holdout-20261025-102740`，对比第十二轮：

- 压缩率上没有损失，反而更好：同画质小 4–6 个百分点，留出集上收益更大，两个指标都是。例外是 butteraugli 下 109 张里 TinyPNG 够不着的多了 4 张（SSIMULACRA2 下反而少了 5 张），完整搜索下"看得出更差"多 1 张；看得出更差的换成了透明背景上的科普线稿图（bicycle、mouse-mechanism、renal-corpuscle；留出集的 college-of-arms、fortepian），是现在离 TinyPNG 最远的一类。
- **提速**：第一版是单线程的，直方图按原图的全部颜色建，5MP 截图上一个调色板（含误差反馈的两遍）要 0.8–1.2 秒、一次抖动映射 0.4–0.7 秒，浏览器里 stripe@2x、tinypng@2x 要 14 秒。改了三处，结果都不随线程数变化（固定分块、按顺序合并）：直方图超过 2^18 种颜色时去掉 r、g、b 的低位合并（加权平均，alpha 不动；最早合并到 2^16 种、连 alpha 一起，浏览器版体积大了 1.3%）；k-means 的最近色分配和不抖动的映射分块并行；抖动按 64 行一段并行，每段从零误差开始，不带误差的像素按颜色查缓存。原生版调色板 0.26 秒、抖动映射 65–94 毫秒，搜索总耗时和 libimagequant 版相当（自动画质 109 张：337 秒对 369 秒）。
- **浏览器**：8 张 5MP 截图多线程 3.6–8.9 秒（libimagequant 版 4.9–9.4 秒）；单线程 8–23 秒（11–21 秒，stripe@2x 从 18 秒变成 23 秒）。WASM 单线程版 928 KB（970 KB），多线程版 1.36 MB。内存反而少了：12MP 峰值 2789 → 2350 MiB，15MP 3425 → 2934 MiB，像素上限不用改；12MP 在多线程版里 31.6 秒完成。
- **浏览器和命令行逐字节相同**：去掉 libimagequant 后，24 张抽样里有 4 张浏览器和 `liqx --finish --preview-pixels 350000` 的输出差几个字节到 1%。线程不是原因（关掉并行结果不变），是数学函数：Oklab 转换里的 `cbrt`、`powf` 在原生版用系统的数学库，在 WASM 里用 Rust 移植的 musl，最后一位不同，偶尔改变 k-means 的取舍。改用 `libm` crate（纯 Rust，fast-ssim2 本来就用它），`powi(3)` 写成乘法，之后两个图集 180 张原生和 WASM 全部逐字节相同，Chrome 多线程版在 8 张截图上也一样。缩小图搜索的大小也挪进了 liqx（`PREVIEW_PIXELS`），`liqx --finish` 默认就用它，浏览器不再自己传，所以命令行不加参数就和浏览器一样（要在原图上完整搜索用 `--preview-pixels 0`；bench 的搜索模式仍默认完整搜索）。
- **剩下的耗时**（Chrome 多线程，8 张 5MP 截图）：SSIMULACRA2 打分 55%，调色板 22%（其中不透明图上 quantette 的 k-means 是单线程的），oxipng 10%，参考图 5%，快速编码 4%，映射 4%。去掉 quantette 候选（`q0`）能让不透明图的搜索快 20–40%，但完整搜索下这些图大 1.8%（Kodak 照片单张最多大 17%）；拿自己的普通调色板（`p0`）顶替也补不回来，Wu 初始化在照片上确实更好。quantette 的多线程模式会让结果随线程数变化，所以没开。
- **去掉的东西**：`imagequant` 依赖（`RGBA` 改用 `rgb` crate），`liqx --quality`、`--backend`，三个要 libimagequant 做对照的实验程序（`palette_lab`、`backend_lab`、`reference_lab`）。误差反馈默认增益从 8 改成 1（`bench.py --liq-feedback` 同步）。liqx 现在 67 个依赖 crate，许可都是 MIT、Apache-2.0、BSD-2-Clause 或 Zlib（`Cargo.toml` 里写了 `license = "MIT OR Apache-2.0"`）。

## 第十四轮：为开源整理

目标：代码质量、尽量少的依赖、尽量快、命令行和浏览器效果相同、不留旧方案的遗留代码。

- **改名、结构**：liqx（libimagequant + x）改名 pngdeer，放到仓库根目录，和 `web/wasm`、`tools/quantlab` 组成一个 Cargo workspace：一份 Cargo.lock，原生版和浏览器版都用 `vendor/fast-ssim2`。模块按职责分开：`color`（Oklab 和双背景合成）、`palette`、`remap`、`search`、`codec`、`par`（固定分块的并行）。
- **命令行只剩一个模式**：`pngdeer IN -o OUT [--target auto|T] [--preview-pixels N] [--variants SPEC]`，就是浏览器版的流程，另外两个给 bench 用的小工具（`--score`、`--upscale`）。去掉了只给 bench 用的“只搜索”模式、旧的普通量化模式，以及只在实验里调过的参数（`--speed`、`--feedback`、`--grain-weight`、`--fixed`、`--importance`、`--dither-mask`、`--exact`、`--small-side`、`--auto-below`、`--auto-cap`、`--verify-steps`、`--preview-margin`、`--finish`），它们变成代码里的常量。整理前后两组图 180 张输出逐字节相同。
- **bench 测真正发布的东西**：`pdT`、`pdauto` 直接调命令行，Python 里重复的收尾逻辑（oxipng、少色图无损、比原图大就回退）删掉了；pngquant 的自动搜索基线 `autoT` 也删了（第一轮的结论已经记在上面）。bench.py 从 1132 行减到 930 行。盲测改认 `pd`，旧运行用 `--challenger liq --results ...` 照样能打开。
- **quantette 换成自己写的 Wu 量化器**：Wu（Graphics Gems II，1991）在 Oklab 里分箱，再用在线 k-means（MacQueen，学习率 count^-1/2，固定的伪随机采样）精修，只用于不透明的图。分箱用 sRGB 能覆盖的 Oklab 范围、32×16×16 个箱时，和 quantette 打平（55 张不透明图：原图上完整搜索 +0.01%，缩小图搜索 −0.15%）；按图片自己的颜色范围分 32³ 个箱时，Kodak 照片会大 14–17%。依赖从 64 个 crate 减到 46 个。变体标签从 `q0` 改成 `w0`。
- **去掉 `q100` 补充候选**（满抖动的 quantette 调色板）：两组图约 1080 次运行里只被选中 7 次。
- **精修调色板**（`p100k`）改用共享的直方图、最近色查找和并行代码：原来遍历 HashMap，浮点累加的顺序每次运行都可能不同。
- **结果没变**（原图上完整搜索，对比第十三轮）：同 SSIMULACRA2 画质体积 109 张 84.4% / 81.1% → 84.5% / 80.9%，71 张 81.6% / 77.7% → 82.2% / 77.8%，TinyPNG 够不着的仍是 6 张和 4 张；butteraugli 109 张 86.3% / 81.8% → 86.3% / 81.5%，71 张 85.6% / 79.1% → 85.0% / 78.7%。发布的默认设置（缩小图搜索）：同画质 84.6% / 81.6% 和 83.3% / 79.0%，自动画质总体积 89.0% 和 84.2%，分数中位数比 TinyPNG 高 0.7 和 0.6（`bench/results/final-main-20261025-120607`、`final-holdout-20261025-120607`、`full-main-…`、`full-holdout-…`）。
- **体积和速度**：WASM 单线程版 970 KB → 839 KB，多线程版 1.36 → 1.24 MB。8 张 5MP 截图在 Chrome 里多线程 3.5–7.7 秒（第十三轮 3.6–8.9），单线程 7.8–20.3 秒；180 张原生和 WASM 仍逐字节相同。
- **质量**：clippy（`-D warnings`）和 rustfmt 干净，`rustfmt.toml` 定了行宽；单元测试（颜色往返、最近色精确）和端到端测试（达到固定目标、同输入同字节、少色图无损、变体解析）；GitHub Actions 跑这三样。`LICENSE-MIT`、`LICENSE-APACHE`；`web/notices.py` 生成浏览器版的第三方许可清单，页面上有链接。fast-ssim2 发布的 crate 里没有 LICENSE 文件，从它的仓库补进了 `vendor/fast-ssim2/LICENSE`。

## 第十五轮：平滑渐变总要抖动

用户拿两张图和 TinyPNG 比，眼睛看出来我们差，分数却说我们好：

- **油画风人像**（1254²）：默认选了不抖动的 `w0`，656 KB、81.8 分；TinyPNG 877 KB、79.2 分。放大看，皮肤碎成一块块平色，块之间有轮廓线，下唇左边发紫；TinyPNG 有颗粒，但明暗连续。只算脸部，SSIMULACRA2 给我们 80.5、TinyPNG 74.6，butteraugli 也是我们好（4.0 对 5.0）。**两个指标都更喜欢平色块而不是抖动的颗粒**，所以搜索一直选不抖动。
- **木头小鹿**（1448×1086，RGBA）：抠图时整只鹿的 alpha 是 240–254，没有一个像素完全不透明。原来只抖动完全不透明的像素，于是整张图一个像素都没抖：选中的 `d50` 和 `d0` 只差几百字节。肚子下面那一大片背光的阴影映射到偏亮、偏橙的颜色上，阴影变浅。
- 试过用“局部平均颜色偏了多少”来量（4×4 到 16×16 的块，算平均颜色和原图的距离，只数超过阈值的块）：TinyPNG 在两张图上都比我们偏得多，眼睛却说它好。看得见的是平色块的**轮廓**，不是平均颜色的偏移，这个量法没用，删了。

改了两处，都在 `src/remap.rs`：

- **半透明像素也抖动**，只要它和四个邻居的 alpha 相差不超过 16（`ALPHA_STEP`）：柔和的阴影、整体 alpha 二百五十几的抠图都算；抗锯齿边缘 alpha 突变，仍然不抖动，原来要防的“误差顺着线稿边缘渗出去”照样防住。
- **平滑渐变无论哪种变体都至少半强度抖动**（`SMOOTH_DITHER`）：一个像素周围 2 像素内有变化、但相邻差别都不超过 `FADE_FROM`（12），就算平滑渐变。人像 78% 的像素算平滑。不抖动的变体（`d0`、`d0r2`、`w0`）在平色区域、文字、边缘和强纹理上照旧不抖动，体积优势留在那里。

结果：

- 人像 656 → 670 KB（+2%，仍是 `w0`，82.4 分），色块的边被颗粒打散；小鹿 292 → 298 KB（+2%），阴影的深度回来了。两张图浏览器版和命令行仍然一样大。
- 默认输出按类别（109 张 / 71 张）：3D 渲染 +8.2% / +10.1%（几乎全是平滑渐变，量最大的 fluent-money-bag +21%，渐变上的色阶没了，8.3 → 10.0 KB，仍比 TinyPNG 的 11.1 KB 小），带透明的照片 +3.5% / +0.8%，照片 +1.3% / −0.9%，图标、插画 0% 到 +1%，界面 −2.8% / −0.2%；约四成的图大小没变。
- 同 SSIMULACRA2 画质体积：109 张 84.6% / 81.6% → 88.8% / 83.2%，71 张 83.3% / 79.0% → 84.5% / 79.7%；够不着的从 6 张和 4 张变成 4 张和 4 张。butteraugli（3-norm，同一个插值方法重算前后）：86.9% / 82.2% → 90.3% / 84.2%，86.1% / 79.7% → 87.3% / 80.4%。自动画质总体积 89.0% → 90.0%、84.2% → 84.4%，分数中位数比 TinyPNG 高 +0.6 和 +0.5。和其他开源工具比（tool_rank.py）：TinyPNG 体积下高 +1.9 / +1.7 分，达到 TinyPNG 画质的 105/109 和 67/71 张（原来 103 和 67）。`bench/results/smooth-main-20261025-142520`、`smooth-holdout-20261025-142520`。
- 速度：一次压一张，新旧版本每张图在 −15% 到 +20% 之间，没有一致的方向。

两个指标在这件事上都和眼睛相反，这一轮的取舍只能靠看图，以后调抖动相关的参数也要先看图再看分。

## 还没解决的

- **透明背景上的科普线稿图**：第十三轮之后离 TinyPNG 最远的一类。bicycle-diagram 在 256 色也够不到 TinyPNG 的 90.0 分，mouse-mechanism、renal-corpuscle、college-of-arms、fortepian 在自动画质下低 1–2 分。抗锯齿的半透明边缘不参与抖动（第十五轮起 alpha 平缓的半透明像素会抖动），平坦色块和细线的调色板分配可能还有余地。（原来最差的 `linear@2x`，同画质体积 116% → 107%（第十二轮）→ 93%，react-dev@2x 123% → 100%，都在第十三轮解决了。）
- **高画质端的 3D / 插画**：第八、九轮补了满抖动、普通调色板和精修调色板三个 256 色候选（第十二轮又给不透明图加了 quantette 调色板），难图平均差距从 −1.27 缩到 −0.69；剩下的见第九轮最后一条（那是 libimagequant 版本的数字）。
- **两个指标都看不出色阶**：第十五轮靠“平滑渐变总要抖动”的规则绕开，没有给搜索一个能量化色阶和轮廓线的信号（比如 Netflix 的 CAMBI）。哪些地方算“平滑”是一个阈值，用盲测校准会更可靠。
- **大图搜索**：原生版第二轮后已经不慢于 TinyPNG，浏览器版第五轮后 5MP 在 10 秒内；瓶颈仍是 SSIMULACRA2，缩小图粗搜的代价是体积大 1.5%。原生版也可以用 `--preview-pixels`，但 bench 里没开。

## 复现

```bash
cargo build --release
python3 bench/bench.py
python3 bench/bench.py --images bench/images-holdout
python3 experiments/palette-feedback/butteraugli_check.py bench/results/latest tinypng,pd70,pd75,pd80,pd85,pd90,pd95
```

- `butteraugli_check.py`：用 butteraugli 给一次 bench 运行的输出重新打分，写到 `<run>/butteraugli.csv`。需要 Pillow 和 numpy。
- `tool_rank.py`：第十一轮的横向比较，把每个工具的输出并成体积–画质前沿，和 TinyPNG 比。
- `ui_diag.py`：第一、二轮的诊断，对比 TinyPNG 和同体积 pngquant 输出的调色板、平坦色还原和误差位置。

前几轮用到的 `ui_exp.py`、`liqexp.py`（驱动 liqx 的旧量化模式）和 `palette_lab`、`backend_lab`、`reference_lab`（要拿 libimagequant 做对照）都已删除，结果留在上面各轮里。第十四轮之前的数字和名字（`liqx`、`liqT`、`q0`）是当时的版本。
